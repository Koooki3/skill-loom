# 项目自身如何发布、升级与持续维护

## 版本对象

分别版本化工具版本、JSON schema、公开示例、用户私有profile、上游skill固定commit、本地适配补丁与验收任务集。工具升级不自动升级skills；模型升级不自动修改用户偏好；来源新增不自动获得写权限。

当前工具版本为0.2.1，JSON采用 schema 1。第一版不提供无感迁移；不兼容的数据应明确拒绝或在新文件中转换，保留原件。发布前将新增字段的可选性、旧版读取行为、迁移方法和撤销方法写进 CHANGELOG。

## 维护入口与责任

Bug报告应附最小复现、工具/宿主/OS版本和匿名化证据，不附原始会话或凭据。新功能以真实任务缺口为起点，说明现有能力为什么不足。来源建议须给完整仓库与SKILL路径、许可证、固定commit、使用案例和适配成本。

贡献者负责候选实现与测试，维护者负责范围和兼容性，一名未参与实现的评审者负责检查重要变更的行为和遗漏。独立评审没有发现问题不等于形式化保证。对小文档修订使用相称的校验，不强迫每次执行全套多agent流程。

## 发布流程

1. 整理变更与当前能力边界，确认文档中的命令可运行。
2. 本地运行单元测试、离线demo、发布检查；涉及宿主集成时执行该宿主验证。将未安装/不可用平台标未验证。
3. 使用一份私有真实环境做只读盘点；涉及实际变更时先生成、审核计划，应用后检查并演练回退。
4. 确认仓库不含本地路径、raw日志、凭据、用户配置、第三方未授权运行包或备份。
5. 提交清晰版本记录，推送后检查GitHub Actions；只有成功结果才能报告CI通过。标签和release记录对应完整commit。

GitHub Actions中的测试矩阵覆盖Windows/Linux与Python 3.10/3.12。首次执行前它只是配置，必须等远端结果。工作流以只读仓库权限运行，测试无需服务凭据。依赖升级由维护者评审，不在技能运行时偷偷执行包管理器。

## 用户升级

固定使用release tag或commit。在新目录/虚拟环境安装候选版本，保留旧目录。依次跑测试、离线demo、当前profile/目录的只读检查，然后用一项小变更验证计划、应用与回退。若新建议突然大规模增加技能或删除既有规则，先解释差异并核查验收标准，不能按“版本更高”直接接受。

维护记录存放在源码之外，使删除开发checkout或切换版本不会丢失回退证据。不要将旧journal当可重建缓存。schema变化只在新副本上试迁移，并对哈希、路径与状态做回归测试。

## 衡量项目是否变好

跟踪实际任务通过率、回退/故障率、误路由、未验证声明、重复能力数量、端到端成本与耗时，以及升级成功率。只报告定义清楚、样本已记录的量。来源覆盖和新技能数量是运维指标，不是任务质量。

季度式回顾可以检查是否仍需要每一个模块、门控、角色和文档；没有实际收益的机制应简化。维护频率由使用者决定；本仓库不默认开启定时抓取、日志监控、自动提交或通知。

## 0.2.0 升级与撤销

本次相对最新正式发布0.1.1增加推荐、Claude观察和使用复核命令，采用MINOR升级；先前main中的0.2.0是开发版本，不再叠加虚构的小版本。包元数据、Python版本常量与CITATION保持0.2.0。

schema仍为1，新增观察元数据和使用报告策略字段是可选的；新读取器仍接受有效旧报告与 `min_sessions` Python参数。未知重叠的报告改取最大值且不拼接门槛，可能使先前开发版的候选消失，这是有意的保守修正。重新从显式原始输入生成观察后复核，不把旧报告的累计值当作唯一会话数。

回退时保留新旧源码环境及各自观察输出，切回0.1.1标签。0.1.1没有新增的 `usage`/`recommend`/`observe-claude` 命令；不要向旧版调用这些接口，也不要降级后继续使用开发版“相加报告”的判断。没有全局技能事务需要撤销。

0.2.0 的 Codex 观察新增可选 `skill_signal_basis` 字符串，旧版读取器可忽略；`skill_md_reads`、计数与 `load-signal` 状态保持兼容。它们表示工具参数中的路径引用，不验证实际读取。旧报告可继续按这一弱信号解释；需要新标记时从原始显式输入重新生成，不改写旧证据。

## 0.2.1 文档补丁与撤销

当前补丁补齐人工决策历史、重新评审条件和研究来源，不改变 CLI 行为、schema 1 或依赖。选择 PATCH：没有新的可执行服务或宿主集成能力。手工记录示例不由 CLI 读取。需要撤销时切回 v0.2.0 源码，保留私有证据；没有全局技能事务需要回退。
