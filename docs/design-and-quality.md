# 六个难点如何落到可验证的设计

本项目把“可持续迭代”分成发现、理解、选择、适配、验收和运行六个不同问题。它们的错误成本不同，不能由一个模型分数或一次成功演示统一替代。

## 1. 及时发现：覆盖范围和时效必须可见

“全世界优质 skills”不存在完备、稳定、可验证的目录。可实现的目标是：建立多来源候选池，知道哪些来源检查过、何时检查、哪些不可用，对高价值领域缩短发现延迟。

来源层可组合官方仓库、领域维护者、精选索引、GitHub检索、论文/产品更新和用户提交。第一版实现固定来源 SHA 对比 `discover` 与显式公开关键词的 GitHub仓库检索 `scout`；其它供应源是扩展点，不伪装成已接入服务。索引发现仓库后仍需定位具体 SKILL.md，不能把仓库搜索结果当作可安装 skill。

```powershell
python -m skillloom scout --query 'agent skills research in:name,description,readme' --query 'SKILL.md evaluation in:readme' --per-query 10 --out '<private-state>/scouting.json'
```

一次最多五条查询、每条最多20个结果。查询会发送给公开 GitHub API，必须用通用能力词，不能带私有项目名称、内部故障描述或用户原始任务。远端失败不回退为“没有新技能”。生产服务可使用官方授权客户端处理 API 配额，不能从运行环境搜集令牌。

推荐的运营指标包括来源检查覆盖率、上次成功检查距今时间、从首次发现到本地验证的延迟、候选采用率、采用后的回退率。覆盖率的分母只能是明确登记的来源集合，不能声称覆盖整个互联网。监控频率、网络预算和安静通知策略由用户选择，第一版不偷偷开启后台服务。

## 2. 质量评判：硬性条件、用户相关性和证据分开

采用前的硬性条件包括：来源固定、许可证经审查、权限与副作用可接受、可在目标宿主运行、本地行为测试通过。高星标、高总分或知名维护者不能抵消硬性缺口。

候选排序使用用户可修改的五维权重。`rank` 的结果名为 **queue_score**，只是调查优先级，不是成功概率。0到4分必须给出证据引用；没有引用的分数按未知处理。示例权重没有经过优化实验，不能当作所有用户的最佳配置。

| 维度 | 0：尚无有效支持 | 2：部分支持 | 4：较强支持 |
|---|---|---|---|
| task_fit | 与实际任务无关或未判断 | 覆盖部分输入/产物 | 直接修复已复现缺口且覆盖相邻边界 |
| evidence | 只有宣称 | 静态检查或小样本正例 | 正反例、回归、保留案例均有可核验证据 |
| maintainability | 失效资源/未知依赖 | 来源固定但适配成本较高 | 结构清晰、依赖明确、更新与回退可复现 |
| efficiency | 无数据或明显冗余 | 任务质量可用，成本未充分比较 | 同一任务集总成本/延迟有可复核改善且质量不降 |
| portability | 不可用工具或隐含平台条件 | 单宿主验证，降级路径明确 | 声称支持的宿主/OS组合有真实运行证据 |

1分和3分用于两档之间，须写明理由。评分者为人或 agent 都应报告证据，不以权威口吻填补未知。本地适配版本与原上游分别评分，不能把上游宣称直接继承给本地版本。

校准方式：保留一部分任务不参与修改；定期比较排序与实际采用后的结果；统计高分失败、低分有效和误拒绝案例；修改权重前保存旧版与理由，用同一保留任务比较。偏好变化与评分错误分开处理。没有足够样本时保持简单规则，不训练一个难以解释的“质量模型”。

## 3. Gap 分析：从产出合同回溯能力

需要的能力来自用户目标与验收要求，而不是从工具列表反推“缺什么就装什么”。能力图至少包括：任务类型、输入、输出、领域约束、所需能力、现有技能/内置工具提供者、依赖，以及验收证据。

`gaps` 对比 profile 的 `required_capabilities`、catalog 的 `capabilities` 与匿名观察中的需求/失败原因。它有三条关键分支：环境故障先修环境；已有提供者出错先复现并适配；没有提供者才进入检索或自制候选。所有建议仍需核查宿主内置能力和项目工作流。

```powershell
python -m skillloom gaps --profile examples/user-profile.json --catalog catalog/local-skills.example.json --observations examples/observations.json --out '<private-state>/gaps.json'
```

该命令不会自动理解所有原始成果。真实系统需要 agent 或维护者从报告、测试、构建记录和用户反馈提取结构化观察，记录原证据位置，再运行规则。原因不确定时标 `unknown`，不能一概怪 skill。对一次高影响故障可立即修复；对普通重复故障优先建立最小复现，不机械要求某个次数。

搜索与自制的决策依据是适配成本：有可信、窄范围且能通过任务集的候选就适配；现有候选带大量无关规则、私有工具或授权扩张时，提取需求后自制小 skill。自制同样要来源/事实边界、正反例和版本记录。

## 4. 控制冗余：管理能力组合，而非技能数量

冗余至少有四种：同名多入口、不同名同触发、重复正文/参考、技能依赖中循环重复调用。过多技能还会抬高发现元数据、维护与回归测试成本。相反，研究统计与科研绘图虽然关联很高，却有不同验收目标，不应仅凭关键词重叠合并。

`portfolio` 对能力集合相似度和用户自定预算给出候选；相似度高不等于冗余。人工检查正反例、产物类型、授权边界和实际依赖后，选择合并、收窄、保留互补关系或退役。第一版实现能力重叠检查，尚不自动构建语义调用图或识别所有自然语言冲突。

```powershell
python -m skillloom portfolio --profile examples/user-profile.json --catalog catalog/local-skills.example.json --out '<private-state>/portfolio.json'
```

一个可持续组合应有明确层次：宿主原生能力、少量通用 skill、按需领域 skill、项目专属 skill，以及不进入运行发现目录的候选/退役区。安装前先问“哪一个已存在的入口应负责这个请求”。相邻领域的差异写在触发边界中；普通任务只加载当前需要的正文与参考。

容量预算是提醒，不是自动删减指令。例子中的45个技能/6000描述字符只是本次环境的可读预算。对小型团队可以更少，对多个独立领域可以更多。未观察到使用不等于低价值；没有充分覆盖样本时只标未验证。

## 5. 客制化：小范围接入，显式偏好，可撤销

部署自迭代服务的第一步是建立可编辑的用户档案：主要任务与交付标准、常用项目、语言与文档习惯、允许检查的记录范围、输出根、授权边界、成本/延迟预算、宿主和必要工具。优先读取用户已明确给出的要求；不从用户名、目录语言、浏览历史或无关文件推测敏感偏好。

快速接入可采用三阶段：

1. **只读基线**：用户选择 profile，`doctor` 只报告OS、Python和几个命令是否存在；显式 inventory 指定技能根；保存当前哈希与配置归属。
2. **小型试点**：选择两三类实际高频任务，测现有流程，补最小缺口，在隔离候选区验证；把环境问题与技能问题分离。
3. **受控运行**：只对已授权范围产生候选和报告；将来源监听、日志归纳、申请变更和实际应用拆开。新增采集范围、外部动作或费用需遵循用户授权。

用户档案留在私有状态目录；公开仓库提供去身份化模板。档案变动需有时间、来源（显式用户要求或已验证环境）和撤销方式。用户画像不能悄悄写成全局命令，也不能通过“长期记忆”绕过用户对记录的控制。第一版是本地 CLI 与 agent 工作流，并非多租户托管服务；多租户隔离、加密存储、团队权限和删除请求需要独立工程实现。

## 6. 真正通用：共享合同，保留宿主差异

可通用的是技能内容、证据格式、候选生命周期、验收与事务原则；目录优先级、权限、tools、subagent、hooks和模型行为不能假装一致。项目采用文件级核心和薄适配文档；详情见[兼容性合同](compatibility-contract.md)。

宿主版本变化时重新探测发现与hook契约；模型变化时重新跑触发/来源/产出案例；OS变化时重测路径、链接、编码、依赖。缺少功能则降级：没有subagent就SOLO；没有可靠Stop hook就显式执行gate；没有连接器则生成本地候选；不能访问日志则用用户提供的事件。降级要可见，不能在新宿主上声称完成了旧宿主的验证。

## 项目自身也是被维护的对象

Skill Loom 的 schema、代码、示例、文档、依赖和适配结论均有版本。发布新版本需要用旧版本数据读入测试、错误/回退测试、至少已有支持平台的 CI、文档命令校验，以及实际本机演练。不得通过升级工具同时无审查地改写用户技能或迁移其宿主目录。

用户选择固定release/commit；升级在单独checkout或venv中试跑 `demo`，再读取自己的inventory/profile做只读检查；比较新旧建议和变更计划，确认已有本地补丁与journal可用后再切换工具版本。失败时恢复旧工具与旧配置，运行中的skill版本独立保留。

参见[发布与维护](releasing-and-governance.md)。目前没有远程自动更新器；这是明确的范围界定，不以未来路线图冒充已实现能力。

## 还需要持续检查的失败面

候选可能包含提示注入、恶意脚本、依赖混淆或突然变更的许可证；日志可能包含私有内容；评分可能过拟合常用案例；自动修复可能掩盖验收标准变化；并行agent可能争写同一目录；缓存清理可能误把最终产物当派生文件；文档可能比CLI更快过时。对应措施分别是源代码审核和固定来源、最小数据导出、保留任务集、版本化验收合同、单一写所有者、精确归属与hash计划、CI与文档更新触发。

这些控制降低的是具体失效风险，不保证“永远安全”或“自动变好”。每轮都需要能解释：改了什么、为什么值得改、哪些证据支持、哪些条件未验证，以及如何停止或恢复。
