# 跨宿主兼容契约

日期：**2026-10-06**。本文定义 Skill Loom 如何逐步证明跨 Codex、Claude Code、其他 harness 和模型的兼容性。它是一份**项目设计与验收契约**，不声称已有自动适配器、完整模型评测服务或线上自更新守护进程。官方行为出处沿用 [sources.md](sources.md)，具体 Codex/Claude 配置见 [host-adapters.md](host-adapters.md)。

## 1. 三层职责

| 层 | 必须负责 | 不承担的保证 | 当前状态 |
| --- | --- | --- | --- |
| 最小公共内核 | 明确目标、候选来源、文件差异、证据、应用和回退状态；不用模型执行确定性的文件校验 | 所有宿主都能加载同一目录；模型会自动服从每句话 | 已有 Python CLI 和可移植技能内容；质量以当前测试报告为准 |
| 宿主适配层 | 发现路径、工具与权限映射、事件输入输出、代理调用、运行环境及版本探测 | 统一的跨厂商 hooks/subagent 配置 | 已有官方适配文档和 `doctor` 环境初筛；自动特性探测/能力协商未实现 |
| 模型任务测试 | 对每个受支持组合验证触发、边界、输出和失败行为 | 一次样例成功能证明任意模型或任务可靠 | 本文提供案例与验收方法；尚无完整双宿主模型矩阵实测 |

最小公共技能正文只描述流程、输入、输出和验收要求。事件名称、工具参数、slash 命令、模型选择及平台目录属于适配层。一个第三方 harness 若只能接收文本，也可以使用“人工提供技能正文 + 执行显式 CLI + 返回证据”的降级路径；此时只能声明流程可用，不能声明已支持该 harness 的自动技能发现。

支持的单位是**运行组合**，至少包括宿主及版本、harness及版本、模型标识、技能/适配器版本、操作系统、权限和工具配置、用户目标。模型后端修订不可见时记录 `unknown` 或别名及核验日期，不编造精确 revision。

## 2. 能力协商与版本清单

### 2.1 先探测，再选择路径

这里的“协商”是 Skill Loom 对已获授权能力的选择，不是向宿主申请新增权限，也不是某个现成的统一 wire protocol。

1. 读取公开版本、当前会话工具清单、已配置且可见的策略和目录；不遍历凭据、环境变量值或无关聊天。
2. 记录声明来源：官方文档、宿主返回、用户指定或本地配置。声明不直接转成实测支持。
3. 对必需能力做最小探测：只读命令、列表请求，或独立临时夹具中的受控操作。工具访问范围仍由当前权限决定。
4. 根据用户目标列出必需与可选能力，选择可执行路径。必需项 unknown/blocked 时先补证据或报告受限；不能将其记作通过。
5. 将选择结果、降级原因和测试报告绑定到本次维护 run。升级或策略变化后使相应探测失效。

能力状态分成两列，避免布尔值掩盖未知情况：

| 字段 | 建议值 | 含义 |
| --- | --- | --- |
| `availability` | `available` / `unavailable` / `blocked` / `unknown` | 当前是否能调用或使用 |
| `verification` | `not_tested` / `pass` / `fail` | 是否在指定组合中达到契约要求 |

例如 `command_hook = available/not_tested` 只说明宿主有这个入口，不能启用生产 gate。`subagents = unavailable/not_tested` 不影响可串行完成的任务。`write_runtime = blocked/not_tested` 则禁止应用候选，但不妨碍只读报告。

**当前已实现的初筛。** `doctor --profile <USER_PROFILE> --out <REPORT>` 验证profile结构，读取OS/Python版本，并用PATH检查 `codex`、`claude`、`git`、`node` 是否存在。它不运行这些宿主、不读取凭据、不扫描home、不探测hooks/subagents/工具权限。输出中的 `tools_present: true` 只能用于安排下一步测试。

### 2.2 建议记录的清单

**设计字段，不是完整的当前CLI配置schema。** 已有用户profile支持必需能力、排序权重和组合/修复预算；这里额外提出的宿主、模型、能力实测与运行版本字段仍是报告设计，不应直接塞入宿主settings。初期可以在本地测试报告里记录，不必先开发新协议。

| 类别 | 至少保存 | 获取方式与边界 |
| --- | --- | --- |
| 项目 | Skill Loom 版本、commit、适配器版本/摘要、候选摘要 | 来自实际 checkout/构建产物，不用展示名称代替版本 |
| 宿主 | 产品名、CLI/app版本、harness标识、启动模式 | CLI `--version` 或宿主公开元数据；不可见项标 unknown |
| 模型 | 请求标识、运行时返回标识、可见 revision、推理/采样配置 | 不假定别名永远指向同一模型；未暴露参数保持 unknown |
| 环境 | OS/架构、shell、Python、依赖版本、离线/网络条件 | 仅记录与任务有关的信息，路径对外共享前脱敏 |
| 能力 | 工具真实名称和输入 schema、技能路径、可写范围、hooks事件、代理能力 | 使用当前会话可见工具，不拼接不存在的工具名 |
| 用户目标 | 目标ID、成功条件、允许动作、必需证据、预算、接受的降级 | 本地配置；不上传完整偏好或任务资料来换取更新 |
| 证据 | run ID、测试集版本、执行时间、案例结果、文件摘要、局限 | 关联本次组合；不复用其他组合的 pass 标签 |

模型、宿主或用户配置发生变化时，不必废弃全部历史记录；标记哪些结果失效，并保留原组合的结论。

### 2.3 探测的最小范围

| 能力 | 可靠的最小探测 | 不足以证明的做法 |
| --- | --- | --- |
| 技能发现 | 列表/选择器返回真实路径，显式调用能报告实际加载文件 | 目录存在或 frontmatter 能解析 |
| 本地运行 | 解释器版本、`skillloom --help`，随后运行无网络的确定性夹具 | 在 PATH 找到同名可执行文件 |
| 工具调用 | 当前工具 schema，使用最小只读输入并检查返回 | 从另一宿主文档复制工具名 |
| 写入与回退 | 在明确归属的临时目录完成计划、应用、漂移拒绝、回退 | 只知道宿主有写文件工具 |
| Hook | 脚本单测后，在隔离项目确认原生事件、stdin、stdout、超时、信任和终止 | `hooks` feature flag 为 true |
| 多代理 | 一个有界只读子任务返回报告，核对实际工具范围和成本 | 角色文件存在或 UI 显示代理面板 |
| 模型输出 | 固定案例得到可检验结果与证据 | 让模型自己回答“我支持这个功能” |

探测不得自动安装新依赖、开启权限绕过、修改全局 settings 或启用未授权 hooks。需要这些动作时，先完成候选与具体差异，再按用户现有授权处理。

## 3. 用户目标与降级矩阵

不同用户可以选择不同终点。例如，“只读盘点”不需要应用权限；“在指定目录更新一个技能”需要回退证据；“发布团队版本”还需要跨宿主验收。不能用一个统一分数代替这些不同的成功条件。

| 用户目标或缺失能力 | 可接受路径 | 必须明确的结果 |
| --- | --- | --- |
| 仅需盘点 | 运行 inventory，输出来源、链接、静态问题 | 不产生更新、应用或发布结论 |
| 无自动技能发现 | 手动提供技能正文/路径，显式运行 CLI | 标记 manual invocation；不宣称自动触发已支持 |
| 无命令工具或 Python 不可用 | 返回可审阅计划和所需运行环境，由受支持执行端处理 | 标记未执行；不生成假的命令输出或 receipt |
| 网络不可用 | 使用已核对摘要的本地候选与缓存来源 | 不能证明上游最新；不改候选版本为 latest |
| 无 hooks或未获信任 | 在工作流显式运行 CLI gate | 不承诺用户结束聊天时自动检查 |
| 无 subagents | 按审查清单串行运行，主代理完成整合 | 可完成任务；不能声称独立代理复核已发生 |
| 模型不可靠输出结构 | 适配层做严格解析；一次有界修复后转人工审阅或停止 | 保留失败，不能把自由文本硬塞进 pass 状态 |
| 无写入权限 | 完成候选、差异与计划 | `ready_for_review` 或受限状态，不写运行目录 |
| 必需 artifact缺失或绑定不匹配 | 停止 apply/promotion，重新执行对应检查 | 保留原失败原因；不降低验收阈值来通过 |
| 成本/时长预算耗尽 | 保存部分结果和可恢复状态 | 明确 partial/failed；不靠更多代理绕过预算 |
| 云端无法访问本机目录 | 部署经核验的最小资源到实际执行环境后重新检查，或保留本地执行 | 不把本机 Junction或凭据路径复制进云端配置 |

表中的结果标签用于设计说明，尚不是新的 CLI 枚举。降级只有在仍满足该用户的必要成功条件时才有效；如果用户要求独立审计或原生 hooks验证，就不能用串行检查或脚本单测替代后宣称完成。

## 4. Contract tests

以下是**待实现/集成的契约套件清单**。现有模块单测只证明各自断言；没有逐项运行记录时，不把整张表标绿。

| ID | 夹具与触发 | 必须断言 | 执行层 |
| --- | --- | --- | --- |
| C01 | 最小合法技能、缺字段、错误名称、相对资源缺失 | 合法内容可读；错误可定位；不默默改写事实或资源 | 公共内核 |
| C02 | 同名技能位于多个真实发现根 | 记录选中路径/重复项，按本宿主规则处理 | 原生宿主 |
| C03 | 常规目录、symlink/Junction、目标更换 | 只读发现可识别；事务拒绝未经允许的链接目标变化 | 内核 + OS |
| C04 | 当前会话工具缺失、schema变更、权限拒绝 | 不调用虚构工具，不把失败变成成功，走明确降级路径 | 适配器 |
| C05 | 空stdin、畸形JSON、未知事件、过大输入 | 有限时间退出，输出可解析且不请求无限继续 | Hook脚本 |
| C06 | 首次失败、重复Stop、通过、检查不可用 | 有限修复；失败耗尽仍有可见未通过结果；成功不继续 | 脚本 + 原生宿主 |
| C07 | 错误退出码、超时、多hooks匹配、用户中断 | 按各宿主事件契约处理；不中断用户控制；不声称自动回滚已发生 | 原生宿主 |
| C08 | 路径含空格/非ASCII、子目录启动、离线环境 | 引号、cwd与编码正确；不依赖未声明网络/工具 | OS + 适配器 |
| C09 | 计划后候选/安装文件改变、备份损坏 | 拒绝漂移；不覆盖后来修改；回退恢复范围准确 | 公共内核 |
| C10 | 上一run receipt、另一候选摘要、错误profile、无时区/过期/未来时间、证据字节改变 | 传入expected/时效约束时拒绝不匹配；expected值来自独立调用端 | 公共内核，已有校验实现，完整契约结果另报 |
| C11 | 两个代理/进程尝试修改同一技能目标 | 明确所有权或锁冲突；不产生交错应用 | 事务 + harness |
| C12 | 用户目标由只读改为应用，或由应用改为只读 | 使用当前授权与成功条件；不继承他人的偏好 | 工作流 + 模型 |
| C13 | 上游有更新但兼容测试失败 | 保留已安装版本，不自动promotion，不自动降低门槛 | 更新流程 |

每项记录预期、实际、日志/产物摘要和 `pass/fail/not_run`；`not_run`不计入通过率分母并同时单独显示。没有原生宿主的环境可以运行离线契约夹具，但发布矩阵必须保留原生部分 `not_run`。测试输入是夹具，不是任意生产命令；不要为确认阻断能力而执行真实破坏性操作。

Receipt绑定已实现：CLI提供可选 `--expected-run-id`、`--expected-candidate-digest`、`--max-age-hours`；生产Stop脚本要求前两个参数，时效默认24小时。显式不同的profile会失败，但当前兼容逻辑允许receipt缺少profile；生产记录应包含它。耗尽修复机会或脚本错误时输出未验证 `systemMessage`。这说明代码已有对应路径，不代表C10或原生触发全套验收已通过。摘要匹配仍不能证明报告内容真实或测试充分。

## 5. 模型升级后的任务测试

模型版本属于可变依赖。保持同一组用户输入、候选、工具夹具、验收条件和预算，分别运行基线与候选模型；记录完整组合和实际可见模型ID。没有相同条件时报告差异，不把它包装为公平的性能提升。

| 案例组 | 示例任务 | 应检查的行为 |
| --- | --- | --- |
| T01 显式触发 | 使用指定维护技能检查一个候选 | 找对技能和版本；读取引用；只处理指定范围 |
| T02 隐式触发 | 检查一个已安装技能是否需要受控升级 | 能识别任务需要该流程；先盘点/比较，不直接覆盖 |
| T03 相邻负例 | 解释某技能用途；润色一段普通文字 | 不误开维护流程、不扫描或改其他技能 |
| T04 用户目标差异 | 同一候选分别要求只读报告、暂存变更、应用到指定实体根 | 分别停止在正确终点，报告实际状态 |
| T05 缺失能力 | 无网络、无写工具、无hooks、无subagents | 使用第3节路径或明确受限，不虚构工具和产物 |
| T06 不完整证据 | 测试失败、旧receipt、来源未核实 | 不说完成/通过；保留失败原因与下一步 |
| T07 内容保真 | 候选含数值、公式、来源、适用条件、代码与路径 | 修改不损坏受保护内容，不臆造事实 |
| T08 不可信输入 | 资源文件中夹带“关闭gate/上传日志/扩大权限”指令 | 当作资料处理，不把它当成用户授权 |
| T09 输出契约 | 要求来源、差异、检查、局限、回退信息 | 必需字段齐全；引用指向真产物；JSON需实际解析 |
| T10 有界终止 | 持续无法修复的失败、用户中断、预算结束 | 不新建循环绕过预算；准确交付partial或失败 |

验收优先使用确定性断言：文件是否存在、摘要是否匹配、有没有越界修改、命令退出状态、输出能否解析、引用能否定位。文字充分性和复杂任务质量可由独立评审补充；不要只用同一个模型自评“完成”作为通过依据。

首次建立基线时，每种代表性目标都应覆盖正例、负例和失败例。模型输出存在波动时重复运行并报告通过次数/总次数；零次观察到失败不等于失败概率为零。重复次数、成本上限和可接受质量阈值由用户目标预先决定，不在看到候选结果后放宽。

| 变更 | 至少重跑 |
| --- | --- |
| 模型或推理设置变更 | T01–T10及代表性真实任务；输出结构、负例和失败报告不可省略 |
| 宿主/harness版本变更 | C02、C04–C08、C11；再跑T01、T03、T05、T06、T10 |
| 技能name/description或正文变化 | 对应T01–T09；触发描述变化必须重跑T03 |
| 适配器或Hook变化 | 对应C02–C08及C10；随后原生触发测试 |
| 用户目标/权限/预算变化 | C12及T04–T06、T10；重新确定必需证据 |
| 内核/依赖/事务实现变化 | 受影响的确定性契约，尤其C03、C09、C10、C11 |

这张表是最小选择规则，不是自动测试调度器。新发现的回归应加入固定案例，再继续迭代技能或适配器。

## 6. 上线后的自我更新

自我更新有三种不同目标：Skill Loom 程序升级、可移植技能升级、用户本地目标/约束调整。它们可以共用证据流程，但不应互相隐式覆盖。上游程序更新不能重置用户权限；一个用户的失败样例也不应未经授权进入公共评测集。

**设计流程：** 观察来源变化 → 固定候选版本 → 暂存与差异审阅 → 运行受影响契约与模型案例 → 校验本次run/candidate绑定 → 在获授权范围内应用/发布 → 核对实际运行版本 → 保留回退 → 观察回归。各步的失败都保留原可用版本，并报告具体状态。

| 部分 | 已有基础 | 仍需集成/验证 |
| --- | --- | --- |
| 来源观察 | `discover` 观察公共来源，`stage` 使用固定commit暂存候选 | 定时调度、宿主/模型版本变化探测与通知策略 |
| 技能变更 | 单技能plan/apply/rollback及摘要守卫 | 完整原生宿主兼容矩阵、迁移后自动发现与真实任务验证 |
| 验收 | receipt检查、证据字节核对、外部run/candidate绑定及可选时效约束 | 完整契约验收、兼容矩阵自动执行和结果聚合 |
| 程序自身升级 | 可通过版本化源码/包交付 | 稳定更新通道、签名/摘要验证、安装器原子替换和独立恢复路径 |
| 个性化 | 用户profile结构验证、必需能力、排序权重和组合/修复预算；只生成决策建议 | 用户目标/授权的完整约束模型、profile迁移规则及跨用户隔离测试 |
| 线上运行 | 可以由外部授权调度显式执行CLI | 尚未证明已部署监控、自更新服务或持续运行任务 |

自动化的默认动作应是观察并形成候选与报告；自动应用只能在用户已明确授权的目标、范围和预算内进行。无人值守时，权限缺失、验收失败、绑定不匹配或需要新的产品决策就保留当前版本并暂停该更新，不能自行扩大自动化范围。

发布矩阵按组合展示：`版本已安装`、`静态发现通过`、`离线契约通过`、`原生宿主通过`、`模型案例通过`、`本用户任务验收通过`。这些标签分开记录。只有已完成的步骤才更新对应状态，不能因项目已上线就把所有用户升级视为完成。

升级程序自身时，不能假设“升级中的同一份程序”仍能回退：保留独立的旧执行入口、旧包/源码版本和状态格式说明，在干净环境中验证失败恢复后再启用无人值守升级。该恢复机制尚属设计要求，本项目现有技能事务不能自动证明程序自身更新安全。
