# Weekly supplement: revisit decisions under changed conditions

Run initiated 30 October 2026 and resumed during that day's repository check.
This supplement retains the original manuscript/PDF/TeX's 6 October scope.
It describes a documentation improvement, not a new learning algorithm.

## Local need and evidence

The existing playbook asks maintainers to record rejection reasons but supplies
no worked handoff showing when those reasons should be reconsidered. During this
review four registered upstream heads changed; head changes alone did not establish
a local requirement to install them. A reusable example can make the next review's
inputs explicit without adding a persistent runtime or a new global skill.

A private, read-only sample after 23 October 04:08:35 UTC through 30 October
00:57:08 UTC selected one Skill Loom conversation and 913 structural records.
Static inspection found 39 user-maintained skills, no errors and no warnings.
The sample spans seven calendar days but only one input file; the usage window
is insufficient and no deactivation candidate was proposed. Earlier intervals
belong to the same conversation and are retained separately. Neither completion
events nor path-reference counts establish accepted task outcomes. Causal task
benefit remains unknown.

## Theory and design decision

SkillHone preserves diagnoses, revisions, evidence and decisions across sessions,
with separated optimization and evaluation roles [1]. Its study includes a fixed
development set and benchmark evaluation, but its stated limitation is evolving
one skill in isolation. We use the record linkage idea, without claiming its
benchmark gains or implementing its permission architecture.

Skill-V uses outcome/rubric disagreements and historical replay to revise skill
boundaries. Its limitations include stale historical evidence when an environment
changes and no explicit skill deletion [2]. We infer that old decisions should
retain their scope and that changed conditions require a new review, not an
automatic reversal. Neither paper was reproduced.

The [manual guide](../docs/decision-history.md) and
[synthetic example](../examples/decision-history.example.json) specify candidate,
task/environment scope, evidence status, predecessor, reasons and reopening
conditions. The example's successor requests review; no probe is presented as
executed. No CLI consumes the format. Hashes and record links do not verify
semantic truth or provide authorization.

## Source review and rejected alternatives

[Seven source heads](../catalog/source-observation-2026-10-30.json) were checked.
The four changed sources cover MCP SDK guidance, deployment-related assets,
discovery links and scanner reports. Comparison metadata was paginated; selected
patches were read. Binary assets, linked skills and complete dependency/licensing
chains were not audited. No third-party code was executed, adopted or installed,
and registry pins remain unchanged.

We defer a new automatic history store, model-based applicability judge and
dependency migration: this local sample supplies no demonstrated need for their
runtime costs. The current contribution is a portable handoff convention.

## Validation and limits

See [dated validation](../docs/validation.md) for executed release checks.
The two-record scenario is synthetic; it is not field evidence, a decision engine,
or an improvement in task quality, token use or maintenance cost. Native host
hooks, macOS, model-task effects and multi-user personalization remain untested.
The runtime cursor covers only the stated sample interval, not publication time.
